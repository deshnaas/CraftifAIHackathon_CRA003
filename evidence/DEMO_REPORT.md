# Sentinel: demo evidence report

> **All video in this report is synthetic.** The demo clips are a procedurally generated street scene with deterministic digital degradations (darkening, blur, a flat patch, a shift and zoom). No real camera, real lens fault or real detector was used.
> This is a **local CPU prototype**. It does **not** satisfy the CraftifAI Track A requirements (PipeGen flow, TensorRT engine, NVIDIA live run). See [Outstanding requirements](#outstanding-gpu--pipegen-requirements).

Evidence captured on 2026-10-15 from this project folder.

## 1. Purpose

A camera can stay online while its picture becomes untrustworthy, because of darkness, blur, something covering part of the lens, or a camera that has been knocked. A vision pipeline keeps producing output in those conditions, so operators don't notice. Sentinel measures the camera input against a healthy baseline and raises evidence-backed JSON incidents. It puts the stream into an explicit **UNTRUSTED** state when the degradation is severe, and closes an incident only after recovery has actually been observed.

## 2. Implemented workflow

| Stage | What the code does | Module |
|---|---|---|
| **Observe** | Reads a video file, camera or RTSP stream. Skips corrupt frames, reconnects live sources, and redacts credentials from URLs. | `sentinel/source.py` |
| **Measure** | For each frame: brightness, gain-normalised sharpness, obstruction fraction, framing similarity and processing time, each relative to the baseline. | `sentinel/metrics.py`, `baseline.py` |
| **Diagnose** | EMA smoothing, enter/exit hysteresis and dwell timers drive HEALTHY → DEGRADED → UNTRUSTED. Assigns a suspected category. | `sentinel/health.py` |
| **Respond** | Opens a versioned JSON incident with measured values, thresholds, evidence, a frame snapshot and recommended operator actions. Persists events and serves them over the API and dashboard (MQTT optional). | `sentinel/incidents.py`, `pipeline.py`, `server.py` |
| **Verify recovery** | RECOVERING requires 3 s of clean footage (`recover_after_s`) before an incident is *resolved*. If the stream ends first, the incident is *unverified*. | `sentinel/health.py`, `incidents.py` |

## 6. What the health metrics can and cannot show

**They can show** that the camera input has changed measurably compared with a baseline the operator declared healthy. They also show when it did so, which check moved and by how much, and that the change cleared and stayed clear for the verification window.

**They cannot show:**
- **Detector accuracy.** No detector ran, and no ground truth was used. Incidents are labelled `claim: "suspected_input_degradation"`.
- **Physical causes.** A low brightness ratio may be night, a failed IR lamp or a covered lens. A low framing similarity may be a moved camera or a large change in the scene.
- **Real-world performance.** Thresholds were tuned on this synthetic scene, so real cameras will need re-baselining and probably tuning.
- **Proxy limits.**
  - The obstruction proxy only catches flat occluders.
  - Global brightness can miss local darkness.
  - Sensor noise can mask blur.

## 8. Known limitations

- **Synthetic validation only.** There's no real camera, no real lens dirt, darkness or displacement, and no real RTSP stream; reconnects were tested only with simulated captures.
- **Detection paths untested on real data.**
  - The ONNX detector backend has never been executed.
  - External detections were tested only with a hand-written fixture (`tests/fixtures/…TEST_FIXTURE.jsonl`), which is not part of this evidence.
- **MQTT** has not been tested against a real broker.
- **Static baseline.** Re-baseline after an intended change of view.
- **Dashboard testing gaps.** Keyboard Tab navigation was not exercised by real key presses in the embedded browser.
